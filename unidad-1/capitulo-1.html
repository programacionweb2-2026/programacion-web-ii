Capítulo 1. De la Web a las aplicaciones Web: arquitectura cliente-servidor, HTTP y frameworks

Índice Unidad 1Capítulo siguiente →

En Programación Web I hemos abordado tecnologías fundamentales para la construcción de sitios y aplicaciones web desde el lado del cliente, particularmente HTML, CSS y JavaScript. Estas tecnologías permiten definir la estructura de una página, establecer su presentación visual e incorporar comportamientos e interacciones que se ejecutan en el navegador.

Sin embargo, muchas de las aplicaciones que utilizamos cotidianamente requieren resolver problemas que exceden las posibilidades de una solución desarrollada exclusivamente en el navegador.

Pensemos, por ejemplo, en una aplicación web utilizada para gestionar estudiantes de una
universidad. La aplicación debería permitir, entre otras operaciones:

  • identificar a cada usuario;
  • consultar información almacenada;
  • registrar y modificar datos;
  • controlar qué operaciones puede realizar cada usuario;
  • mantener información entre diferentes sesiones;
  • procesar reglas propias del sistema;
  • generar respuestas diferentes según el usuario y la información disponible.

Para implementar estas funcionalidades necesitamos incorporar nuevos componentes y comprender cómo se comunican entre sí.

Programación Web II propone avanzar desde los conocimientos adquiridos en el desarrollo del frontend hacia la construcción de aplicaciones web completas, incorporando procesamiento del lado del servidor, persistencia de datos y herramientas que permitan organizar el desarrollo de aplicaciones de mayor complejidad.

Para ello utilizaremos principalmente Python y Django. Antes de comenzar a trabajar con este framework, resulta necesario comprender cómo funciona una aplicación web y qué ocurre desde que un usuario realiza una acción en su navegador hasta que obtiene una respuesta.

2. De una página web a una aplicación web

Los términos sitio web, página web y aplicación web suelen utilizarse indistintamente. Sin embargo, desde el punto de vista del desarrollo de software resulta conveniente establecer algunas diferencias.

Una página web es un documento que puede ser interpretado y presentado por un navegador. Su estructura se define principalmente mediante HTML y puede complementarse con CSS y JavaScript.

Una aplicación web, en cambio, incorpora además mecanismos de procesamiento que permiten responder a las acciones del usuario, gestionar información, aplicar reglas y producir resultados dinámicamente.

Por ejemplo, un sitio institucional puede presentar información relativamente estable sobre una universidad. Un sistema académico accesible mediante la Web, en cambio, debe permitir que diferentes usuarios inicien sesión, consulten datos, registren inscripciones, carguen calificaciones o realicen operaciones de acuerdo con los permisos que poseen.

La diferencia no depende exclusivamente de las tecnologías utilizadas, sino fundamentalmente del tipo de procesamiento e interacción que la solución necesita realizar.

3. Contenido estático y contenido dinámico

Una primera aproximación para comprender esta diferencia consiste en distinguir entre contenido estático y dinámico.

Contenido estático

Un recurso estático puede ser enviado al navegador sin necesidad de modificar su contenido para cada solicitud.

Entre los ejemplos habituales encontramos:

  • archivos HTML;
  • hojas de estilo CSS;
  • imágenes;
  • fuentes;
  • determinados archivos JavaScript.

Si diferentes usuarios solicitan el mismo recurso estático, el servidor puede entregar esencialmente el mismo contenido.

Contenido dinámico

En una aplicación web, muchas respuestas deben generarse en función de diferentes condiciones.

Por ejemplo:

Un estudiante ingresa al sistema y consulta las asignaturas en las que se encuentra inscripto.

  • qué estudiante inició sesión;
  • qué información existe en la base de datos;
  • qué inscripciones posee;
  • qué permisos tiene;
  • qué operación solicitó.

El servidor deberá procesar la solicitud, obtener la información necesaria y construir una respuesta apropiada.

Esto nos conduce a uno de los conceptos fundamentales de las aplicaciones web: la arquitectura cliente-servidor.

4. Arquitectura cliente-servidor

Las aplicaciones web se apoyan generalmente en un modelo de comunicación denominado cliente-servidor.

En este modelo existen componentes que solicitan servicios y otros que los proporcionan.

Cliente

El cliente inicia una solicitud.

En una aplicación web, el cliente suele ser un navegador como Firefox, Chrome o Edge. El navegador permite al usuario interactuar con la aplicación y es responsable, entre otras funciones, de interpretar HTML y CSS y ejecutar código JavaScript.

Servidor

El servidor recibe solicitudes provenientes de los clientes, las procesa y genera las respuestas correspondientes.

En aplicaciones dinámicas, el servidor puede necesitar ejecutar código, aplicar reglas, consultar una base de datos o utilizar otros servicios antes de generar una respuesta.

5. ¿Qué sucede cuando solicitamos una página?

Supongamos que una aplicación de gestión de tareas dispone de la siguiente dirección:

https://ejemplo.com/tareas/pendientes/

Cuando el usuario accede a esa dirección, simplificando algunos procesos de
infraestructura, ocurre lo siguiente:

1. El usuario realiza una solicitud

El navegador solicita al servidor el recurso /tareas/pendientes/.

2. Se genera una petición HTTP

El navegador construye y envía una HTTP Request.

GET /tareas/pendientes/ HTTP/1.1
Host: ejemplo.com

3. El servidor recibe la petición

La aplicación que se ejecuta en el servidor debe determinar qué funcionalidad corresponde ejecutar para esa URL.

4. La aplicación procesa la solicitud

Puede ser necesario:

  • verificar quién realiza la solicitud;
  • validar permisos;
  • consultar información;
  • aplicar reglas;
  • procesar datos.

En nuestro ejemplo, podría consultar cuáles son las tareas cuyo estado es pendiente.

5. Se genera una respuesta

Una vez procesada la solicitud, el servidor genera una HTTP Response.

6. El navegador recibe e interpreta la respuesta

Si la respuesta contiene HTML, el navegador lo interpreta y representa visualmente para el usuario.

El proceso puede sintetizarse como:

Usuario

↓ Navegador

↓ HTTP Request

↓ Servidor / Aplicación

↓ Procesamiento

↓ Datos / reglas

↓ HTTP Response

↓ Usuario

Más adelante veremos que Django proporciona componentes específicos para organizar prácticamente todas estas etapas.

6. HTTP: la comunicación entre cliente y servidor

HTTP (Hypertext Transfer Protocol) es el protocolo utilizado para el intercambio de información entre clientes y servidores en la Web.

HTTP se basa fundamentalmente en un esquema de solicitud-respuesta:

un cliente envía una solicitud y un servidor devuelve una respuesta.

Por ello utilizaremos permanentemente dos conceptos:

  • HTTP Request: solicitud enviada por el cliente.
  • HTTP Response: respuesta enviada por el servidor.

7. La HTTP Request

Una solicitud HTTP proporciona al servidor la información necesaria para determinar qué operación pretende realizar el cliente.

Entre sus componentes podemos encontrar:

  • un método HTTP;
  • una URL o ruta;
  • encabezados (headers);
  • parámetros;
  • eventualmente, un cuerpo (body) con datos.

Por ejemplo:

GET /productos/15/ HTTP/1.1
Host: ejemplo.com

Esta solicitud podría interpretarse como:

«Quiero obtener la información correspondiente al producto 15».

8. Métodos HTTP

Los métodos HTTP permiten expresar el tipo de operación que se pretende realizar sobre un recurso.

Entre los más utilizados se encuentran:

Método Propósito habitual

GET
Obtener o consultar información
POST
Enviar información o crear un recurso
PUT
Reemplazar o actualizar completamente un recurso
PATCH
Modificar parcialmente un recurso
DELETE
Eliminar un recurso

En las primeras aplicaciones desarrolladas con Django trabajaremos especialmente con GET y POST. Posteriormente estos conceptos también serán importantes para comprender otras formas de construir servicios y APIs web.

Es importante señalar que el significado concreto de una operación depende de cómo esté diseñada la aplicación. Los métodos proporcionan una semántica para la comunicación, pero es el servidor quien implementa el comportamiento correspondiente.

9. La HTTP Response

Una vez procesada la solicitud, el servidor devuelve una respuesta.

Una respuesta HTTP incluye, entre otros elementos:

  • un código de estado;
  • encabezados;
  • un cuerpo con el contenido de la respuesta, cuando corresponde.

Un ejemplo simplificado podría ser:

HTTP/1.1 200 OK
Content-Type: text/html

El navegador recibe esta información e interpreta el HTML para mostrarlo al usuario.

10. Códigos de estado HTTP

El código de estado informa el resultado general del procesamiento de una solicitud.

Los códigos se agrupan en familias:

Familia Significado general

1xx
Información
2xx
Solicitud procesada correctamente
3xx
Redirección
4xx
Error asociado a la solicitud del cliente
5xx
Error durante el procesamiento en el
servidor

Algunos códigos habituales son:

  • 200 OK: la solicitud fue procesada correctamente.
  • 201 Created: se creó un nuevo recurso.
  • 301/302: redirección.
  • 400 Bad Request: la solicitud no pudo procesarse correctamente.
  • 401 Unauthorized: se requiere autenticación.
  • 403 Forbidden: el usuario no posee autorización suficiente.
  • 404 Not Found: no se encontró el recurso solicitado.
  • 500 Internal Server Error: ocurrió un error interno durante el procesamiento.

Estos códigos no son solamente información técnica. Forman parte del contrato de comunicación entre cliente y servidor.

11. Frontend y backend

Frontend

El frontend corresponde a la parte de la aplicación con la que interactúa directamente el usuario.

Entre las tecnologías ya conocidas encontramos:

  • HTML;
  • CSS;
  • JavaScript.

El frontend se ocupa, entre otros aspectos, de la estructura visual, presentación e interacción en el navegador.

Backend

El backend corresponde al procesamiento realizado principalmente del lado del servidor.

Puede ocuparse de:

  • recibir solicitudes;
  • aplicar reglas;
  • validar información;
  • autenticar usuarios;
  • controlar permisos;
  • acceder a bases de datos;
  • generar respuestas;
  • comunicarse con otros sistemas.

En Programación Web II comenzaremos a desarrollar especialmente este segundo componente utilizando Python y Django, sin abandonar los conocimientos de frontend adquiridos anteriormente.

Una aplicación web completa requiere que ambas partes se comuniquen de manera coherente.

12. Incorporación de la persistencia

Hasta ahora podemos ampliar nuestro esquema:

La base de datos permite conservar información más allá de una solicitud particular.

Una aplicación podría almacenar, por ejemplo:

  • usuarios;
  • productos;
  • estudiantes;
  • asignaturas;
  • inscripciones;
  • mensajes;
  • pedidos;
  • tareas.

Pero la aplicación no debería permitir que cualquier usuario consulte o modifique arbitrariamente estos datos. Entre el cliente y la base de datos existe una lógica de aplicación encargada de interpretar las solicitudes y decidir qué operaciones deben realizarse.

Al comenzar a desarrollar aplicaciones web más complejas aparecen problemas que se repiten en numerosos proyectos.

Necesitamos resolver, entre otras cuestiones:

  • ¿Cómo asociamos una URL con una funcionalidad?
  • ¿Cómo procesamos una solicitud HTTP?
  • ¿Cómo generamos dinámicamente HTML?
  • ¿Cómo nos conectamos con una base de datos?
  • ¿Cómo validamos los datos ingresados?
  • ¿Cómo gestionamos usuarios y contraseñas?
  • ¿Cómo mantenemos una sesión?
  • ¿Cómo controlamos permisos?
  • ¿Cómo protegemos la aplicación frente a problemas frecuentes de seguridad?
  • ¿Cómo organizamos el código para que pueda mantenerse y evolucionar?

Sería posible desarrollar soluciones particulares para cada uno de estos problemas. Sin embargo, muchos de ellos son comunes a una gran cantidad de aplicaciones.

Aquí aparece la necesidad de utilizar frameworks de desarrollo web.

14. ¿Qué es un framework web?

Un framework proporciona una estructura, componentes, convenciones y herramientas reutilizables que facilitan el desarrollo de software.

Un framework web no construye automáticamente nuestra aplicación ni decide cuáles son sus requerimientos. Proporciona una base organizada sobre la cual podemos desarrollar nuestra solución.

Entre otras funcionalidades, un framework puede proporcionar mecanismos para:

  • gestionar URLs;
  • procesar solicitudes y respuestas HTTP;
  • trabajar con bases de datos;
  • generar contenido HTML;
  • validar formularios;
  • autenticar usuarios;
  • gestionar sesiones;
  • controlar permisos;
  • aplicar mecanismos de seguridad;
  • realizar pruebas.

15. Framework no significa ausencia de decisiones

Utilizar un framework no elimina la necesidad de comprender cómo funciona una aplicación web.

Por el contrario, para utilizarlo correctamente es necesario comprender:

  • qué problema estamos resolviendo;
  • cómo se organiza la aplicación;
  • qué responsabilidades tiene cada componente;
  • cómo circula la información;
  • qué decisiones de diseño estamos adoptando;
  • cuáles son las consecuencias de esas decisiones.

El framework proporciona herramientas, pero las decisiones de análisis, diseño e implementación continúan siendo responsabilidad del equipo de desarrollo.

Esta idea será especialmente importante durante el Trabajo Integrador de Programación Web II.

17. Actividad de análisis

Antes de comenzar a programar con Django, proponemos analizar una situación sencilla.

Supongamos una aplicación web para gestionar tareas. Un usuario autenticado accede a:

/tareas/pendientes/

y el sistema presenta solamente sus tareas pendientes.

A partir de los conceptos desarrollados en este documento, analizar:

1. ¿Quién cumple el rol de cliente? 2. ¿Qué información debería contener conceptualmente la solicitud? 3. ¿Qué componente deberá recibir y procesar esa solicitud? 4. ¿Qué información necesitará recuperar la aplicación? 5. ¿Dónde podría encontrarse almacenada esa información? 6. ¿Qué decisiones deberá tomar el servidor antes de devolver los datos? 7. ¿Qué tipo de respuesta podría recibir el navegador? 8. ¿Qué conocimientos de HTML, CSS y JavaScript adquiridos en Programación Web I

siguen siendo necesarios?

No buscamos todavía implementar la solución. El objetivo es reconstruir conceptualmente el recorrido de la información.

18. Aplicación al Trabajo Integrador

Sobre esa funcionalidad deberá describir:

Actor → acción → solicitud → procesamiento esperado → información necesaria → respuesta

Por ejemplo:

Actor:
Estudiante
Acción:
Consultar sus inscripciones.
Solicitud:
Solicita acceder al listado de asignaturas en las que está inscripto.
Procesamiento:
La aplicación identifica al estudiante y recupera sus inscripciones.
Información necesaria:
Usuario + estudiante + asignaturas + inscripciones.
Respuesta:
Página HTML con las asignaturas correspondientes.

Este análisis constituye una primera aproximación a la arquitectura del Trabajo Integrador. No se pretende todavía definir modelos, vistas ni código Django, sino comprender el problema desde la perspectiva de una aplicación cliente-servidor.

19. Síntesis

Una aplicación web puede entenderse inicialmente como un sistema en el que clientes y servidores intercambian solicitudes y respuestas mediante HTTP.

El navegador actúa habitualmente como cliente. Desde allí, el usuario genera solicitudes que son procesadas por una aplicación ejecutada del lado del servidor. Esta aplicación puede aplicar reglas, acceder a información persistente y generar una respuesta adecuada.

A medida que aumenta la complejidad aparecen necesidades comunes: enrutamiento, acceso a datos, generación dinámica de contenido, formularios, autenticación, autorización y seguridad.

El concepto central que deberíamos conservar es:

Una aplicación web no es solamente aquello que vemos en el navegador. Es un conjunto de componentes que colaboran para recibir solicitudes, procesar información y producir respuestas.
